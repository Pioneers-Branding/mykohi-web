Question 1

Have we verified that Googlebot, Bingbot, and AI crawlers are actually blocked, or is this an assumption based on our audit crawler?

Finding: When diagnostic tools, Lighthouse, or automated audit scripts request any address on the site, Cloudflare intercepts the request at its edge nodes (172.67.149.195 / 104.21.88.3) and returns HTTP 403 Forbidden with cf-mitigated: challenge and an interstitial verification screen.

Googlebot Reality: Cloudflare validates Googlebot using automated reverse-DNS lookups against Google's official IP ranges (rather than simple User-Agent strings). Google has historically indexed core pages of your site (including your Homepage, /services/, /services/understanding-tms-therapy/, and recent blog posts), confirming that Google has crawled pages in the past.

The Critical Vulnerability: The interstitial challenge page Cloudflare displays serves <meta name="robots" content="noindex, nofollow">. Whenever automated search crawlers, Google Ads verification bots (AdsBot), or legitimate AI search engines encounter this challenge during threat spikes or WAF rule evaluations, they are actively instructed to purge the page from search indexes. Furthermore, real prospective patients using Safari Private Relay, workplace/hospital Wi-Fi networks, or certain mobile data carriers are trapped at this same challenge screen.

Question 2

How were we able to crawl and audit the website if these restrictions are in place?

Because automated direct scrapers were blocked at the Cloudflare perimeter, our team conducted a multi-vector empirical audit utilizing non-restricted channels:

  • Edge Server & Response Header Inspection: Direct HTTP/2 handshake analysis, TLS security verification (Google Trust Services certificate valid to Jan 2027), and DNS resolution across Cloudflare edge nodes.
  • Search Engine Grounding & Indexed Cache: Inspecting the actual URLs, metadata titles, and cached text snippets that Google's index has cataloged for your domain (e.g., your TMS therapy guides, insurance articles, and psychiatric service taxonomy).
  • Public Medical Directory Cross-Referencing: Auditing public registry listings across Psychology Today, Zocdoc, ThrivingCampus, and the NPI registry (which surfaced the conflicting addresses between Centennial and Greenwood Village).
  • Domain Authentication & Email Security: Direct DNS records examination for MX mail routes (Google Workspace), SPF authentication, and DMARC enforcement policies (p=none).
  • Real-Browser Execution: Observing client-side JavaScript challenge payloads (challenges.cloudflare.com) and token exchange parameters in a live browser environment.
Question 3

Have we confirmed that Cloudflare's "Under Attack" mode is enabled?

Technical Confirmation: We confirmed with 100% certainty that Cloudflare is actively serving a Managed Challenge (verified by response headers: cf-mitigated: challenge and runtime parameter cType: 'managed').

Dashboard Context: From outside Cloudflare's administrative dashboard, a Managed Challenge can be produced by any of the following settings:

  1. "I'm Under Attack!" mode toggled on under Security → Settings.
  2. Security Level set to "High", which aggressively challenges IPs with elevated threat scores (frequently including mobile carrier subnets and corporate VPNs).
  3. "Bot Fight Mode" or "Super Bot Fight Mode" set to challenge automated traffic without an exemption for verified bots.
  4. A Custom WAF Firewall Rule that inadvertently applies a Managed Challenge to broad URI paths or regional IP pools.
Key Takeaway: Checking your Cloudflare dashboard under Security → Settings and Security → WAF will pinpoint the exact active rule in under 60 seconds.
Question 4

Lori specifically wants to know whether Google is genuinely experiencing crawling issues right now. How can she verify this?

Lori does not have to rely on external assertions—Google provides direct, internal crawl logs inside Google Search Console (GSC):

  1. Run a Live URL Test (60 Seconds): Log into Google Search Console, paste https://zephyrbehavioralhealthandwellness.com/ into the top inspection bar, and click "Test Live URL". If it reports "URL is available to Google" and renders a screenshot of your actual website homepage, Googlebot is currently reaching your server. If it reports "URL is not available to Google", an HTTP 403 code, or renders the Cloudflare "Just a moment..." screen, Google is actively blocked from crawling your homepage.
  2. Inspect the Crawl Stats Report: Navigate to Settings → Crawl stats → Open Report and examine the "By response" breakdown over the last 90 days. Spikes of 403 (Forbidden) or sudden crawl drops indicate that Googlebot has encountered firewall challenge barriers.
Question 5

What specific corrective actions do we recommend in Cloudflare?

Your webmaster or IT administrator can safely implement these adjustments in under 5 minutes:

  1. Set Security Level to "Medium": In Cloudflare under Security → Settings, ensure the Security Level dropdown is set to Medium (Cloudflare's recommended baseline for normal business operations, not High or Under Attack).
  2. Configure Bot Management: Under Security → Bots, ensure settings do not challenge verified search engines. In Super Bot Fight Mode, set Verified Bots to "Allow".
  3. Update Custom WAF Rules: Under Security → WAF → Custom rules, review any active challenge rules and add the exemption condition: and not cf.client.bot. This ensures verified search bots (Googlebot, Bingbot, AdsBot) pass through freely while malicious bot traffic is still intercepted.
Question 6

Will lowering Cloudflare's security level leave Zephyr vulnerable to cyberattacks?

No, absolutely not. Setting Cloudflare to "Medium" is the industry benchmark for healthcare practices, hospitals, and commercial websites.

What Remains 100% Protected: Cloudflare's automated DDoS mitigation continues to absorb volumetric traffic floods. The Web Application Firewall continues to block known malicious IP addresses, automated vulnerability probes, SQL injections, and cross-site scripting (XSS) attacks. Full SSL/TLS encryption remains active.

The Difference: Setting to "Medium" ensures innocent prospective patients, mobile users, and search engines reach your site without being trapped behind an artificial 5-second checkpoint.

Question 7

What does the acronym "RLS" refer to if mentioned in technical discussions?

The term RLS was not an audit finding in our formal report, but in client meetings it is almost universally a simple mishearing of TLS (Transport Layer Security, the SSL certificate that secures HTTPS), CLS (Cumulative Layout Shift, a Google mobile speed metric), a WAF Rule-Level Setting (or Rate Limiting System), Row-Level Security in databases, or Restless Legs Syndrome in clinical neurology.
